# Changelog

All notable changes to `@shimmerresearch/shimmer-web-sdk` will be documented here.
This project follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- **The Consensys Backup device folder is the MAC id, not the Shimmer name.** `consensysBackupSegments` nests the card tree under `<import-stamp>/<mac-id>/…`, twelve lowercase hex digits, and `downloadSdTree` takes the MAC through a new `macId` option:

  ```
  Backup/2022-11-29_10.36.45/e8eb1b9767a0/data/RN4678_v1_23_1669669660/RN4678_v1_00-000
  ```

  The old name folder produced a tree Consensys walks straight past, so a download that looked complete could not be imported — reported by JC against a bench run. The MAC is also the identifier that cannot drift: a sensor renamed between two trials keeps one folder, where the name split its sessions in two. Lowercase because that is what Consensys writes and what `parseSdLogHeader` reports for the same six bytes inside the file; the two have to agree, and on macOS and Linux the case is load-bearing.

  `macId` is the CONNECTED device's MAC, which is right whenever the card is being read out of the device that wrote it — the only way this transfer path can be reached at all. Reading each session's first file header for the MAC stored in it would be exact for a card physically moved between devices, at the cost of a round trip per session for a case a Bluetooth download cannot produce. A consequence worth knowing: two devices' sessions on one card now land in one folder rather than two, and a test pins that.

  The parameter is optional and the old behaviour is the fallback — Shimmer name from the session folder, then `CONSENSYS_UNKNOWN_DEVICE` — but that fallback is **not** an importable tree. It exists so a download without a readable MAC still lands somewhere sensible, and `consensysMacFolderName` (also exported) returns `null` rather than a guess for anything that is not six bytes of hex, so a caller can tell "no MAC" from "a MAC I could not use" and warn.

- **`InfoMemSdConfig.estimatedExpLengthMin` is now `estimatedExpLengthSec`, because the value is in seconds.** The firmware counts this one in seconds and its sibling in minutes — `experimentLengthEstimatedInSecMsb/Lsb` and `experimentLengthMaxInMinutesMsb/Lsb`, with matching accessors (log-and-stream-common `Configuration/shimmer_config.h:403-406, 539-540`) — so the old name asserted the wrong unit by a factor of sixty. Java agrees for the estimated field (`getTrialDurationEstimatedInSecs()`); only Java's layout comment, "Maximum and Estimated Length in minutes", disagrees, and it is wrong for it.

  The docblocks previously called the unit ambiguous and deferred to a hardware check. That was the honest position when only the Java sources were to hand; with the firmware struct as the oracle there is no ambiguity left, and a name that states a unit ought to state the right one. `maxExpLengthMin` keeps its name: minutes really is what the firmware counts there, and the mismatched pair is the firmware's own asymmetry, now pinned by a test so it cannot be tidied away.

  The two schema fields also carry their units in their labels now, which is the point of resolving it: a host that renders the form no longer shows two adjacent duration fields with no way to tell what either means.

  **Breaking** for anyone reading or constructing `InfoMemSdConfig` by hand. The InfoMem bytes are unchanged, so saved images, devices and the schema's own field keys are unaffected, and no consumer in these repositories referenced the old property name. It still breaks the exported type, so this release takes the minor — `0.2.0`, the first time this project has moved off `0.1.x` — rather than hiding a rename behind a patch bump or leaving a deprecated alias behind for a name nothing ever used.

### Added

- **The factory self-test, over Bluetooth and over the dock.** `SET_FACTORY_TEST` (0xA8) had been in the opcode table with no caller since the table was written, and the dock's TEST component was not in `UART_PROP` at all. `Shimmer3RClient.runFactoryTest(type, opts)` and `WiredShimmerClient.runFactoryTest(type, opts)` now run the suite the firmware runs on the production line and return its report as text; `SHIMMER3_FACTORY_TEST_TYPES` is the four-entry table a host builds its picker from (MAIN, LEDS, ICS, LED_STATES — the firmware's own `factory_test_t`), carrying each suite's expected duration, a default timeout and whether it prints an overall verdict.

  This command is unlike every other one in the SDK, and the shape of the API is a direct consequence. The firmware acknowledges it and then prints the report as **raw ASCII on the same link** — no opcode, no length, no CRC — while its main loop is blocked for the whole suite, up to about seventy seconds for the LED-state walk-through (`Test/shimmer_test.c:22-61`, `Comms/shimmer_bt_uart.c:1285-1293`). So:

  - The report is diverted **before framing**, in each client's notify entry point. Anywhere later is too late: the framer would resync through the text one byte at a time (a report line starts with `/`, which reads as a firmware-version response and swallows what follows), and the temp handlers only ever see whole framed messages, so nothing downstream would see the report at all. What the capture hands back is whatever was **not** report traffic — a status push glued after the `TEST END` banner, a late ACK — and that continues down the normal path.
  - **Every other write is refused** while a capture exists, with a `FactoryTestError` of reason `busy`. The firmware is not merely slow to answer: a command sent now sits in its receive buffer and is acted on a minute later, with its ACK landing in the middle of somebody else's report.
  - **There is no abort command.** `opts.signal` stops the client listening; the sensor keeps printing to its own end. The run therefore enters a `draining` state — the result promise rejects at once, the bytes keep being swallowed, and the link is only advertised as free when the report has really ended. `whenFactoryTestIdle()` is how a host waits that out, and `factoryTestState` / `onFactoryTestStateChange` are how it keeps its own gating honest meanwhile.
  - A **preflight status read** (Bluetooth only, `opts.preflight`, default on) turns "the firmware NACKed" into "the sensor is recording, started from its own button" — a state the host cannot otherwise see. It is deliberately non-fatal when the status read itself fails: a diagnostic must not veto the thing it was diagnosing.

  Over the dock the acknowledgement is a CRC-checked packet rather than a single byte, so `classifyFactoryTestAckPacket` is the dock's half of the same machine: a header-less head is report text, a `BAD_*` packet is a refusal carrying its reason, and a CRC-corrupt packet is one byte to skip rather than text, because the report has not started and one bad byte must not turn the rest of a legitimate packet into report content. On a Shimmer3R the firmware routes the report to the USB CDC port when the sensor is plugged in by USB and to the dock UART otherwise, so the one method serves both. One caveat is documented on the method because a reader of the report needs it: on Shimmer3 the ExG chip test **cannot pass from the dock** — the dock UART and that chip share pins, and the firmware prints so itself — so a FAIL on that line from this transport says nothing about the board.

  HARDWARE-VERIFY: no real Shimmer3 or Shimmer3R has run any of this. In particular, that the ACK and the report's first bytes really do share one BLE notification, and that a status push can arrive glued to the `TEST END` banner, are the two shapes the capture is built around; both are reasoned from the firmware's single-buffer transmit path.

- **`parseShimmerFactoryTestReport`, and one report grammar for all three device families.** The Verisense report parser has been split into a shared core (`src/devices/factoryTest/report.ts`) driven by a grammar object, plus two grammars: the Verisense one, and a new Shimmer3/Shimmer3R one (`src/devices/factoryTest/shimmerReport.ts`). The two firmwares print the **same envelope** — `TEST START`, `Firmware version:`, `Overall Result = PASS | FAIL (0x…)`, `TEST END` — and the same ` - <ID> - PASS: <detail>` line shape, so nearly all of the existing grammar was already right; what differed was the id token, the temperature format, and a handful of line forms.

  `parseShimmerFactoryTestReport(text)` detects the family and returns the same parsed shape either way: `S3R_TEST_00NN` ids resolve to stable names through `SHIMMER3R_FACTORY_TEST_ID_NAMES`, and a Shimmer3 report, which prints **no ids at all**, still yields tests (with `id: null`) named from their content. It copes with the line forms the firmware really produces: the dash variant (` - S3R_TEST_0014 - FAIL - BT hasn't initialised`), a not-applicable line with no verdict word, `WARNING` as a third verdict, the repeated ADS1292R id for two chips (merged, worst verdict winning), the LED narration and the LED-state walk as informational tests that are never part of the fail mask, and lines the firmware truncated at its 128-character buffer — which drops that line's terminator and glues the next line onto it. `shimmerFactoryTestReportToCsvRows` emits the same two-row shape as the Verisense helper.

  `parseVerisenseFactoryTestReport` is now a thin wrapper over the shared core and every `Verisense*` type is an alias of the shared one, so nothing that consumed it needs to change. Its output is pinned byte-for-byte by inline snapshots of seventeen real report fixtures, taken **before** the refactor: none of them moved.

  HARDWARE-VERIFY: every Shimmer3/3R line shape here is transcribed from firmware source, not from a captured report. Worth knowing for the first bench run: on Shimmer3 the Bluetooth firmware-version verdict is a bare ` - PASS` with no words at all, so it parses as a generic numbered test rather than as the Bluetooth one. Nothing in that line can name it; the cheapest fix is a firmware wording change.

- **`toggleLed()` and `setRedLed(on)` on `Shimmer3RClient`.** `TOGGLE_LED_COMMAND` (0x06) flips the firmware's red-LED override, which holds the lower LED solid red above the SD-error and battery indications — the "which sensor is this one" aid. Two things a host needs to know are now documented and handled: the firmware **never clears the flag**, so it survives a disconnect until it is toggled again or the sensor loses power; and because the command is a toggle with no set, `setRedLed` reads status bit 7 either side of it, writes nothing when the LED is already as asked, and throws rather than reporting success if the sensor's flag does not follow. While streaming, `toggleLed` writes without waiting for an ACK — every inbound byte belongs to the data plane then, so the wait would time out on a command the firmware did in fact run.

### Changed

- The real-world-clock docblocks on `Shimmer3RClient` no longer say the device holds LOCAL civil time. It does not: desktop Consensys and the Java dock driver both write a plain Unix epoch, and hardware set by either reads back as UTC. That claim was the Verisense console's convention carried across by mistake, and it had already misled one page into displaying a correctly-set sensor a whole timezone offset adrift. No behaviour changed — `setRtcTime`, `writeRtcFromHostTime` and `writeInfoMemConfig` were already writing `Date.now()`.

- **ExG (ADS1292R) configuration, as a codec rather than as byte literals** (ported from PR #70 by jyong15). The ECG/EMG/respiration expansion board is configured by two 10-byte per-chip register banks, and until now the SDK could only move them around as opaque bytes: `parseInfoMem` handed back `exg1`/`exg2`, the field schema called them `bytes10`, and the demo app put them on screen as hex for a human to read a datasheet against. Nothing could say what a bank meant, and the only way to set one was three hardcoded 16-bit instruction arrays on `Shimmer3RClient`.

  The new `src/devices/exg/` codec is the single definition of those banks for all three places they appear — InfoMem, an SD-log header, and the live radio commands. `decodeExgRegisters` turns one bank into named settings with the Java GUI's own labels (and, for a PGA gain, the numeric gain); `encodeExgRegisters` goes back, forcing the datasheet's must-be bits; `detectExgPreset(exg1, exg2)` names what a pair of banks is — ECG, EMG, ExG test signal, respiration, custom or off — as tolerantly as the desktop does, keying only off the input-selection nibbles and the respiration bits so that the fields firmware rewrites never change the answer; `applyExgPreset` produces the banks **and** the enabled-sensors bitmap for a chosen preset, including the resolution flags, the sampling-rate-to-data-rate coupling and the conflicting sensors the desktop disables when you click a preset tile; and `updateExgSetting` / `applyExgKnobEdits` change one named knob at a time, preserving every other bit and enforcing the desktop's respiration coupling rules with typed errors. Resolution is not a register field — it lives in the sensor bitmap, and `exgResolutionFromSensors` reads it back. Every byte value in the module carries the driver `file:line` it came from, because none of it can be checked without an ExG board.

  Both clients gain `readExgConfig()`, `writeExgConfig(exg1, exg2)` and `applyExgPresetLive(preset, resolution)` over GET/SET_EXG_REGS. The write deliberately departs from the Java driver, which fires SET_EXG_REGS and does not verify, relying on a timeout-then-disconnect failsafe if the write silently fails (ShimmerBluetooth.java:4212-4216): here the SET is followed by a GET read-back and a comparison — ignoring only REG8, the read-only lead-off status register the chip never echoes — so a bad write surfaces as an error at the call site. Disabling ExG live never writes zeroed banks, because the chip forces its must-be bits and such a write could not read back; it drops the ExG bits from the sensor bitmap, exactly as the driver does. On classic Shimmer3 the whole command set is gated on the firmware version through the newly exported `shimmer3SupportsExg` / `deriveShimmer3FirmwareVersionCode`, a port of the `ShimmerVerObject` capability ladder, so an ExG call on firmware without the commands fails immediately with the version in the message instead of hanging to the response timeout. `parseSdLogHeader` now also returns `exg1`/`exg2` from header bytes 56-65 and 66-75, so a recorded file can be asked which preset produced it.

  `enableEMG16Bit()`, `enableECG16Bit()` and `enableEXGTestSignal16Bit()` are kept and are now one-liners over `applyExgPresetLive`, which makes the preset arrays the one source of preset bytes and **fixes three byte errors** in the hardcoded arrays they used to carry, each checked against the driver's reference arrays:

  - The ExG test signal wrote `0x15` to CH1SET/CH2SET on both chips where the driver has `0x05` (SensorEXG.java:1844-1861). Bits 6:4 of those registers are the PGA gain, so the SDK selected gain 1 where the driver selects gain 6 — a six-fold amplitude error on the square wave someone is looking at precisely to decide whether an ExG board works.
  - EMG chip 2 wrote `0xe1` to CH1SET/CH2SET where the driver writes `0x81` (SensorEXG.java:1812-1836). Both power the channel down, but the SDK also left a gain of 12 in the bits of a powered-down channel, so a read-back could never match a device the desktop software had configured.
  - The joined-clock bit (CONFIG2 bit 3, `OSCILLATOR_CLOCK_CONNECTION`) was set on chip 1 unconditionally. The driver sets it only when `ShimmerVerObject.isSupportedExgChipClocksJoined` (:712-723) — a Shimmer3R with the unified ExG board, or a Shimmer3 with unified ExG board revision 4 or later. It is now a named field driven by the hardware version, so a Shimmer3R still gets it and a classic Shimmer3, whose board revision is not knowable from the hardware id, keeps whatever bit it already had rather than having one forced on. Preset detection continues to ignore that bit when matching, which is why banks differing only there still identify correctly.

  A behaviour change comes with the unification: EMG now enables the chip-1 resolution flag only, following the driver (SensorEXG.setExgChannelBitsPerMode, :2162-2182), because the EMG preset powers chip 2 down. The old helper enabled both chips and streamed two channels of powered-down noise.

- **Calibration-dump transfer on `Shimmer3RClient`** — `readCalibDump()` (GET_CALIB_DUMP_COMMAND 0x9A) and `writeCalibDump(bytes, opts?)` (SET_CALIB_DUMP_COMMAND 0x98). The existing `readCalibration()` reads the per-sensor 21-byte blocks and learns nothing else about them, so a host could not tell a real factory calibration from a default the firmware seeded, nor put a calibration back at all. The dump carries the provenance the per-sensor commands leave out — sensor id, range, and the calibration timestamp whose all-zero value marks a seeded default — and `readCalibDump` returns both the raw bytes and the `parseCalibDump` result so a caller can inspect it or hand it straight back.

  A dump's size is not fixed and is not known before reading it: the first two payload bytes are a little-endian u16 and the total is that value **+ 2**. `readCalibDump` therefore reads 128 bytes at offset 0, takes the total from the header, and pages the remainder — rejecting a length of 0 (what an unprovisioned calibration memory reads back) or one beyond `MAX_CALIB_DUMP_BYTES`, newly exported as the 4096 the Java driver uses, rather than paging after a number a corrupt device sent. Writes go forward from offset 0 because the firmware takes the total from the first chunk's header and counts the rest in; an out-of-order write is discarded silently, without even a NACK. `opts.update` (default `true`) follows the last chunk with `updateCalibDump()` (0x9B), which is what makes the written dump take effect.

  Note the direction of precedence, documented on the method: the firmware regenerates its dump FROM the configuration bytes whenever InfoMem page D (or, on a Shimmer3R, page C) is written, so a later `writeInfoMemConfig` supersedes a dump written here. Write the dump after the configuration, not before.

  HARDWARE-VERIFY: unexercised against real hardware. The chunked sequence matches both the firmware handler and the Java driver's `readMem(GET_CALIB_DUMP_COMMAND…)`, but no Shimmer3R has answered it over this transport — which is why `readCalibration()` still prefers the per-sensor commands for streaming calibration.

- **InfoMem configuration over Bluetooth on `Shimmer3RClient`** — the radio client could read the configuration memory one page at a time (`readInfoMem(address, length)`) and had **no write path at all**, so a host could inspect a sensor's configuration over Bluetooth but never apply one; configuring a Shimmer3 or Shimmer3R meant docking it. This adds the write half and the whole-image layer above both, mirroring `WiredShimmerClient` method for method so the dock and the radio read as one API: `writeInfoMem(address, data)` (SET_INFOMEM_COMMAND 0x8C, `[len][offsetLo][offsetHi][data…]`, resolving on the firmware's ACK), `readInfoMemBytes()` / `writeInfoMemBytes(bytes, opts?)` for the full 384-byte image, `readInfoMemConfig()` / `writeInfoMemConfig(config, opts?)` for the decoded configuration, and `updateSdLogConfig()` (UPD_SDLOG_CFG_COMMAND 0x9C) / `updateCalibDump()` (UPD_CALIB_DUMP_COMMAND 0x9B) for the two regenerate-from-InfoMem commands the firmware exposes.

  Page addresses are never hard-coded: the client reads the device's own hardware and firmware versions and resolves them through `resolveInfoMemLayout`, because a Shimmer3 on old firmware addresses its InfoMem at the absolute MSP430 0x1800/0x1880/0x1900 while a Shimmer3R uses flat 0/128/256 — and this client talks to both. Both version reads are already cached per connection, so every entry point asks rather than making callers remember to.

  Write chunks default to **64 bytes over a framed (BLE) transport and 128 over a byte stream**, overridable with `opts.chunkBytes`. 128 is the firmware's own ceiling for the command and what a byte stream carries happily; 64 is the size the EEPROM brand-record write is proven to survive on real BLE hardware, where a command crosses several notifications into a receive buffer that a larger record has overflowed before. `writeInfoMemConfig` writes the real-world clock FIRST and only then the image — the order desktop Consensys uses — and an RTC failure aborts the write rather than being tolerated, so the InfoMem is never touched after a half-successful clock set. `opts.verify` (default `true`) re-reads the image and byte-compares it against what was sent, excluding the ranges a device write legitimately diverges in: the MAC the firmware overwrites from its own transceiver and the config-delay / config-file-creation flag byte it rewrites. That comparison now lives in one place, `compareInfoMemExcluding` (exported), instead of being private to the dock client.

  Every one of these refuses, before putting a byte on the wire, if the client believes it is streaming. The firmware NACKs every SET while it is sensing (`ShimBt_isCmdBlockedWhileSensing`), and a NACK arriving partway through a chunked write would leave a half-written configuration on the device — much worse than a clean refusal, and previously indistinguishable from a dead link because it surfaced as an ACK timeout.

  HARDWARE-VERIFY: no real Shimmer3R has taken an InfoMem write over this transport yet. The command layouts and the ordering are the firmware's and the Java driver's, but that the device accepts the write, applies it, and regenerates its SD configuration is unconfirmed — as is the 64-byte BLE chunk size holding up across a full 384-byte image.

- **Full InfoMem configuration model and a declarative field schema** (`devices/infomem/`) — the codec previously modelled a useful subset of the 384-byte configuration image: sampling rate, the sensor-enable bitmap, GSR range and expansion power, the ExG banks, Bluetooth baud, derived channels, the SD/trial block and the MAC. Every other byte round-tripped untouched but could not be read or written by name, so a host could not offer the configuration a docked Consensys session offers. This adds the rest of what the Java driver's `configBytesGenerate` writes: the IMU block (`imu.wrAccelRange`/`wrAccelRate`/`wrAccelLpm`/`wrAccelHrm`, `gyroRange`, `imuRate`, `magRange`, `magRate`, `altAccelRange`, `pressureOversampling`, `altMagRate`, `altAccelRate`), the SD timing block (`sd.btInterval`, `estimatedExpLengthMin`, `maxExpLengthMin`), the six 21-byte kinematic calibration blocks as verbatim `Uint8Array`s, and the 21-slot sync-node MAC list. `generateInfoMem` still layers every field onto the image it was parsed from, so bytes no field models — the MPU9150-DMP calibration blocks, config setup byte 6, the reserved regions — survive a read-modify-write byte-for-byte; a test asserts exactly that, because it is what lets a host edit one field of an unfamiliar firmware's configuration without destroying the rest.

  Two fields are **composite**, and getting either wrong corrupts a neighbour: `gyroRange` is a 2-bit field in config byte 2 plus an MSB in config byte 4 (a 3R gyro reaches ±4000 dps, which does not fit two bits), and `pressureOversampling` is 2 bits in config byte 3 plus an MSB in config byte 4. Both MSBs are written only for Shimmer3R contexts. Three positions in this area disagree between the Java driver's declaration comments and its own usage; the firmware struct (`log-and-stream-common Configuration/shimmer_config.h`) settles each, and the codec follows the firmware: the pressure MSB lives in config byte 4 bit 0 (Java declares it under a "Config Byte0" comment but uses it with `idxConfigSetupByte4`), the LIS3MDL alt-mag rate lives in config byte **5** bits 0-5 (Java's comment says byte 4, where its 0x3F mask would have overlapped the alt-accel rate and the gyro-range MSB), and there is **no** mag-rate MSB at all — the shift Java declares for one is commented out in both its parse and generate paths and has no counterpart in the firmware, so writing it would have silently overwritten alt-mag-rate bits. `wrAccelLpModeMsb` (config byte 4 bit 1) exists in the firmware with no Java field; it is left untouched rather than modelled from a guess.

  Also new: `SHIMMER3_INFOMEM_FIELD_SCHEMA`, a declarative description of every configurable field (label, description, kind, the layout key its byte index resolves through, bit shift and width, value/label option tables, group, and which hardware generations it applies to) with `readInfoMemFieldValue` / `writeInfoMemFieldValue` / `resolveFieldIndex` / `infoMemFieldsFor` / `inferShimmer3Generation`. A host renders a configuration editor from the schema rather than hand-writing a control per field, and the same renderer serves a Shimmer3 with the old IMU, one with the new IMU, and a Shimmer3R — the fields a generation does not have are declared, not deleted, so the editor can say so. Fields carried only by MPU9150 DMP firmware and options no LogAndStream build honours are deliberately absent from the schema while remaining preserved in the bytes. **HARDWARE-VERIFY: the layout is a source-to-source port cross-checked against the firmware struct; no value has been written to a device through this codec. `inferShimmer3Generation`'s expansion-board revision thresholds are transcribed from the Java driver and unchecked against boards, and the experiment-length units are inconsistent across the firmware field names, the Java accessors and the Java layout comment — the codec stores the raw u16 and documents the ambiguity, so confirm before labelling a control.**

- **Device status and battery on `Shimmer3RClient`** — `getStatus()` (GET_STATUS_COMMAND 0x72 → `[0x8A][0x71][status0]…`) and `getBattery()` (GET_VBATT_COMMAND 0x95 → `[0x8A][0x94][BattStatusRaw ×3]`), plus `onDeviceStatus` for the STATUS_RESPONSE the firmware pushes unprompted whenever docking, SD logging, streaming or the USB rail changes (`ShimBt_instreamStatusRespSend`). An inquiry reports how a sensor is _configured_; only the status bytes say whether a recording is actually running, whether the real-world clock has been set since the sensor last lost power, or whether the firmware failed to open its SD file — none of which was reachable before. New pure codec `parseShimmer3StatusBytes` + `Shimmer3DeviceStatus` (bit assignment from `ShimBt_assembleStatusBytes`, log-and-stream-common `Comms/shimmer_bt_uart.c:2920-2932`): `docked`, `sensing`, `rtcSet`, `sdLogging`, `streaming`, `sdPresent`, `sdError`, `redLedOn`, and `usbPluggedIn` as `boolean | null` — the second status byte exists only under `#if defined(SHIMMER3R)`, so a Shimmer3 reports `null` rather than a misleading `false`. Battery reuses the dock's `parseBatteryStatus`: the three payload bytes are the same `BattStatusRaw` record the dock UART carries, voltage curve and all. `onDeviceStatus` fires **only while idle** — once streaming, every inbound byte belongs to the data plane and the schema parser consumes a push without recognising it; poll `getStatus()` instead. A `getStatus()` in flight suppresses the callback so a solicited reply is not also reported as news. **HARDWARE-VERIFY: exercised against a scripted loopback in both framed (BLE) and unframed (serial) shapes, not yet against real firmware — in particular the unsolicited-push path and the ACK-prefix state (SET_INSTREAM_RESPONSE_ACK_PREFIX_STATE 0xA3).**

- **`Shimmer3RClient.readDeviceVersion()`** — GET_DEVICE_VERSION_COMMAND (0x3F → `[0x25][hw]`), cached like `readFwVersion` and reusing the existing `parseShimmer3DeviceVersionResponse`. Worth asking despite the client's name: the two platforms share this firmware and command set, so a Shimmer3 reached over classic Bluetooth answers here too — and answers GET_STATUS with one byte where a Shimmer3R sends two. Reporting hardware 3 narrows the client's status framing accordingly. Both version caches are now cleared in `connect()`, since a reconnect may be to a different sensor. **HARDWARE-VERIFY: not yet read from a real device through this client.**

- **`onDisconnect` on `BaseShimmerClient`** — `((reason?: Error) => void) | null`, wired into `Shimmer3RClient`, `Shimmer3Client` and `WiredShimmerClient` alongside their existing status emission (unchanged). Fires for an **unexpected** transport drop only — never for an application's own `disconnect()`. That asymmetry is the point: a handler that reconnects would otherwise reconnect after its own teardown, so every consumer would have to filter its own action back out. Previously the only signal was `onStatus('Device disconnected')`, a log line indistinguishable from any other by anything but its text. Fires at most once per connection, collapsing both a transport that reports one drop twice and the common "drop, then `disconnect()` to clean up" pair. Verisense keeps its own `emit('disconnected')` event and is unaffected.

- **Configuration option tables for both Shimmer3 families** (`src/devices/shimmer3/sensorOptions.ts`) — 34 tables of `[configValue, label]` pairs ported **verbatim** from the Java driver (`ShimmerDriver/.../com/shimmerresearch/`), one `file:line` citation each: LSM6DSV accel/gyro range and the shared accel+gyro rate; LIS2DW12 range and its high-performance / low-power rates; ADXL371, LIS2MDL and LIS3MDL rate and range; BMP390 / BMP581 oversampling and rate; BMP180 / BMP280 resolution; GSR range in both resistance and conductance wordings; LSM303DLHC and LSM303AH accel range, HR/LPM rates, mag range and rate; MPU9X50 gyro/accel range and mag rate; and the Bluetooth baud rates. Verbatim matters twice over — the labels are what a researcher recorded in a trial log beside their data, and the values are register encodings that the obvious derivation (label index) gets **wrong** in at least four tables: the LSM303AH orders its four accel ranges `{0, 2, 3, 1}`, the LIS3MDL rates are raw CTRL_REG1 codes (`0x3E` = 80 Hz sits above `0x3A` = 20 Hz), the LSM303DLHC high-resolution rates skip code 8 (low-power-only 1620 Hz, so 1344 Hz is code 9), and its mag range starts at 1. Each such oddity is preserved with a comment and pinned by its own test. Also `SHIMMER3_SENSOR_LABELS` (friendly names for every sensor-enable bit) and `samplingRateToDivisor` / `divisorToSamplingRate` / `SHIMMER3_SAMPLING_RATES_HZ`. Two deliberate divergences from Java: the LSM6DSV rate table stops at the 13 labelled values although the Java config array runs 0-13 (its last entry pairs with no label), and the sampling-rate list is **not** a port — Java holds a rate as a double and has no picker list, so the conventional Shimmer3 rates are used and the comment says so. **HARDWARE-VERIFY: the tables are a source-to-source port; no value in them has been written to a device through this SDK.**

- **CSV row and column helpers** (`core/csv.ts`) — `csvRow`, `objectClusterColumns` and `objectClusterRow` beside the existing `csvCell`. A stream of `ObjectCluster`s is not a table: each frame carries the channels that frame happened to have, some signals in both a raw and a calibrated version and some in only one. Emit `oc.fields` per frame and the moment one frame's field list differs — a channel the parser could not calibrate, say — every later cell shifts left and the file still reads as valid data. So `objectClusterColumns` fixes the column set once (headers `NAME_RAW` / `NAME_CAL` / `NAME`, order following the negotiated schema rather than an alphabetical order the reader would have to undo) and `objectClusterRow` projects each frame onto it, writing `null` for a column that frame lacks. The projection matches a column's kind **exactly**, which `ObjectCluster.get` deliberately does not — it reads a null kind as "any kind", so a kindless column (the timestamp) would otherwise pick up a raw field sharing its name. `csvRow` adds no trailing newline: a file destined for Excel on Windows wants CRLF and only the caller knows that.

- **`usbDfuBootloader` in the parsed status payload** — status byte 65 bit 0 (the second status-flags byte; byte 26's flags are full): the installed bootloader's DFU mode has the USB CDC transport (settings page reports bootloader version ≥ 3). Reported by firmware carrying the DEV-939 app changes; `null` on older firmware (shorter payload) — unknown, never treated as unsupported. Lets hosts steer users to USB vs BLE updates without a try-and-see DFU-mode request.
- **Dual bootloader name prefixes in the DFU picker** — v3 (BLE+USB) bootloaders advertise `Verisense-DFU-XXXX` (harmonised with their USB product string so the same MAC-suffixed name identifies a unit on either transport), while fielded v2 bootloaders advertise `Verisense-BL-XXXX` forever. `buildVerisenseDfuRequestDeviceOptions` now filters on both; new export `VERISENSE_DFU_BOOTLOADER_NAME_PREFIXES` (the legacy `VERISENSE_DFU_BOOTLOADER_NAME_PREFIX` is unchanged).
- **Verisense Secure-DFU over USB serial** (`dfuSerial.ts`) — a self-contained SLIP + Nordic serial secure-DFU driver for the combined BLE+USB (v3) bootloader's USB CDC port, driven over any `SerialDfuTransportLike` (`WebSerialTransport` satisfies it directly). Same signed `.zip` packages as BLE DFU; the flow mirrors nrfutil's `dfu usb-serial` (ping → PRN 0 → MTU → command object → CRC-validated data objects), resumes interrupted transfers from the last completed object, rolls back only the current unexecuted object on a device-CRC mismatch (the write position cannot be rewound past executed objects), and surfaces the bootloader's extended-error codes as readable messages ("Signature verification failed", ...). New exports: `VerisenseSerialDfu`, `slipEncode`/`SlipDecoder`, `crc32`, the `SERIAL_DFU_*` opcode/result tables, `VERISENSE_USB_DFU_PORT_FILTERS` (VID 0x1915 / PID 0x521F — the bootloader's DFU port, distinct from the application's 0x520F), `VERISENSE_USB_DFU_REENUMERATION_DELAY_MS`, and `isUsbDfuUnsupportedError`. Companion client method `requestUsbDfuBootloaderReboot()` sends the `DFU_MODE` property over the serial transport: firmware on a v3 bootloader ACKs and reboots into the bootloader's USB port ~300 ms later; firmware on a BLE-only (v2) bootloader NACKs (classified by `isUsbDfuUnsupportedError`) so apps can fall back to the BLE flow. **HARDWARE-VERIFY: not yet exercised against a real v3 bootloader (none exists until the DEV-939 firmware bench pass); protocol behaviour is unit-tested against a scripted mock.**

- **RTC-from-host write in the docked config-write flow (`WiredShimmerClient` / `SmartDockClient`), phase P2.** Brings the docked config write to parity with desktop Consensys's `CallableWriteConfig.call()` (`BasicDock.java:1556-1587`), which writes the device's real-world clock from the current PC time **before** the chunked InfoMem write. `writeInfoMemConfig(config, opts)` gains `opts.setRtc` (**default `true`**, matching desktop): when set — and the identity supports RTC-via-UART — it writes the RTC first, then the InfoMem, as one atomic queued unit. Ordering, skip, and failure semantics are ported from the Java: the RTC write is **skipped (not failed)** on identities that do not support it (`isSupportedRtcConfigViaUart`, ported from `ShimmerVerObject.java:405` — Shimmer3 needs SDLog/LogAndStream/StroKare firmware, Shimmer3R is supported on any firmware), and a **RTC-write failure ABORTS the config write** (the InfoMem write is not attempted), exactly as desktop rethrows the RTC `ExecutionException` before reaching the InfoMem write (`BasicDock.java:1564-1573`) — deliberately not best-effort. A new low-level `writeRtcFromHostTime(nowMs?)` (default `Date.now()`, injectable for testability) writes the 8-byte, LSB-first 32.768 kHz tick payload to `MAIN_PROCESSOR.RTC_CFG_TIME` (0x04) — ported byte-for-byte from `CommsProtocolWiredShimmerViaDock.writeRealWorldClockFromPcTime` + `UtilShimmer.convertMilliSecondsToShimmerRtcDataBytesLSB`. `SmartDockClient.writeInfoMemConfig(slot, config, opts)` threads `setRtc` through unchanged. Finalization of a plain config write is unchanged and identical for Shimmer3/3R (the device regenerates its SD config on the next undock / power-cycle; the DFU reboot-then-rewrite dance is out of scope). New exports: `msToRtcBytesLE`, `isSupportedRtcConfigViaUart`. **HARDWARE-VERIFY: the RTC payload format and the `RTC_CFG_TIME` write have not been exercised against a real dock.**

- **SmartDock multi-slot base support (`SmartDockClient`), phase D2.** Adds Base-6 / Base-15 multi-slot bases on top of D1's single-device `WiredShimmerClient`. A SmartDock exposes two channels: a **base control** channel speaking short ASCII `SDx$` commands (used to read the base version, query per-slot occupancy, and switch the _active_ slot), and a **per-Shimmer** UART channel onto which the base routes the active slot (spoken with the D1 binary `$`-header protocol) — two distinct FTDI serial ports on real hardware, as in the Java driver (`SmartDock.java:226-229`). Ported from `com.shimmerresearch.managers.dockManager.SmartDockUart` / `SmartDockUartListener` and `com.shimmerresearch.comms.wiredProtocol.SmartDockActiveSlotDetails`. **Scope: READ-ONLY** — dock info, occupancy, slot select, and per-slot identify/status. No config writes, no SD/mass-storage (the `SDC` with-SD-access connect exists in the oracle but is not driven), no bootloader/flashing. Public API: `getDockInfo()` → `{ hardwareType (base6/base15), firmwareVersion, slotCount }` (from the `SDV$` → `V,hw,fwId,major,minor,internal` reply); `getSlotOccupancy()` → per-slot occupied/empty (from `SDQ$` → `Q,<bitmap>`); `selectSlot(n)` → issues `SDP,NN$`, awaits the `P,NN` confirmation with the **ported ~10 s slot-change timeout** (`SMARTDOCK_RESPONSE_TIMEOUT_SLOT_CHANGE`), verifies the slot, then applies the **1500 ms** without-SD settle delay (`SLOT_CHANGEOVER_DELAY_WITHOUT_SD_CARD`) and resyncs the per-Shimmer stream; and `identifyDockedShimmer(n)` / `getDockedShimmerStatus(n)` which select the slot then **compose (do not duplicate)** `WiredShimmerClient` against the now-active slot. Normal base-command reads use the ported **1000 ms** timeout (`SMARTDOCK_RESPONSE_TIMEOUT`). Like D1, the base UART is an **unframed byte stream**, so the client accumulates bytes and extracts `\r\n`-terminated lines (`extractBaseLine`), ignoring unrecognised/partial lines to resync after garbage; an `E` error line rejects. Transport injection is **required** (base transport; throws without one). A one-line addition to `WiredShimmerClient` — `resyncStream()` — lets the composed D1 client drop stale bytes after a slot re-route. **Verification status: code-complete pending hardware** (see README for slot-change timing, occupancy semantics, and base6-vs-15 detection items). New exports: `SmartDockClient`, `SmartDockClientOptions`, `SmartDockInfo`, `SlotOccupancy`, the base command / connection-type / hardware-id tables (`SMARTDOCK_BASE_CMD`, `SMARTDOCK_CONNECTION_TYPE`, `SMARTDOCK_DEFAULTS`, `BASE_HARDWARE_IDS`), and the pure codec (`buildBaseCommand`, `buildSelectSlotCommand`, `extractBaseLine`, `classifyBaseResponse`, `parseSmartDockVersion`, `parseSlotOccupancy`, `parseActiveSlot`, `baseHardwareType`).

- **Wired / dock UART client (`WiredShimmerClient`), phase D1.** Talks to a Shimmer sitting in a BasicDock/Base over the dock's FTDI **UART** (host↔device) — a protocol entirely separate from the Bluetooth LiteProtocol used by `Shimmer3Client` / `Shimmer3RClient`. Ported from the Java driver's `com.shimmerresearch.comms.wiredProtocol` package. **Scope: identify + status + property-level config for a single docked device.** No mass-storage/SD, no firmware flashing, and no multi-slot Base state machine (those are later phases); the dock protocol has no streaming. Transport injection is **required** — a docked Shimmer is only reachable over the wired link, so `connect()` throws without an injected `ShimmerTransport` (the transport should report `capabilities.framed = false`; configure the port at `UART_DOCK_BAUD_RATE` = 115200 8N1). Public API: `connect()`/`disconnect()`, `identify()` → `{ mac, hardwareVersion, firmwareVersion, expansionBoard }` (reads MAC → HW/FW version → daughter-card ID in `BasicDock` order), `getStatus()` → `{ voltage, percentage, chargingStatus, adcValue }`, property-level `getConfig(prop)` / `setConfig(prop, value)` / `getConfigAll()` over the `UART_CONFIG_COMMANDS` table (`mListOfUartCommandsConfig`), and a low-level `readInfoMem` / `writeInfoMem` escape hatch (the InfoMem _layout_ is deliberately not interpreted in D1). A pure codec (`src/devices/dock/protocol.ts`) provides packet build/parse — `$`-header packets addressed by component + property with a length byte, payload and a Shimmer-specific CRC (`src/devices/dock/crc.ts`, seed `0xB0CA`, distinct from the Verisense CRC-16/CCITT-FALSE so it is a **new** implementation, verified byte-for-byte against the Java `ShimmerCrc` compiled and run directly). Like `Shimmer3Client`, the client accumulates the **unframed** serial byte stream and extracts complete packets with a length-aware parser (`wiredPacketLength`), tolerant of packets split, dribbled, or coalesced arbitrarily; a bad-CRC packet triggers a single-byte resync, and device error responses (`BAD_CMD` / `BAD_ARG` / `BAD_CRC`) reject with their reason. **Verification status: code-complete pending hardware** (see README for the items needing a real dock). New exports: `WiredShimmerClient`, `WiredShimmerClientOptions`, `WiredIdentity`, the `UART_*` command/component/property tables, `WIRED_DEFAULTS`, `CHARGING_STATUS_BYTE`, the CRC functions, and the codec functions (`buildUartPacket`, `parseUartPacket`, `wiredPacketLength`, `parseMacId`, `parseVersionInfo`, `parseBatteryStatus`, `parseExpansionBoard`, etc.).

- **Classic-Bluetooth Shimmer3 client (`Shimmer3Client`).** A client for the pre-3R Shimmer3 over an RFCOMM/SPP byte stream. It speaks the same LiteProtocol as `Shimmer3RClient` and reuses the shared pure pieces verbatim (`OPCODES`, `SensorBitmapShimmer3`, `CHANNEL_FORMATS`, `TIMESTAMP_FIELD`, the byte utilities, and the GSR calibration), so only the genuinely classic-specific behaviour is new. Transport injection is **required** — Web Bluetooth cannot open an RFCOMM socket, so `connect()` throws a clear error without an injected transport (a platform such as a React Native Android module supplies one; `SHIMMER3_SPP_UUID` is exported for it). The key difference from the BLE clients: RFCOMM is **unframed** (no MTU, no message boundaries), so the client runs a length-aware **byte-stream parser** (`shimmer3ControlMessageLength`) that accumulates inbound bytes and extracts complete LiteProtocol messages regardless of how they are split or coalesced — robust to ACKs and inquiry responses arriving in 1-byte dribbles, split across chunks, or coalesced together. The connect **handshake** is ported from the Java `ShimmerBluetooth#initialize` sequence: a best-effort `STOP_STREAMING` safety write, a dummy `GET_SAMPLING_RATE` read to flush the RFCOMM buffer, then `GET_DEVICE_VERSION` (0x3F) and `GET_FW_VERSION` (0x2E); the streaming timestamp width (u24/u16) is derived from the reported firmware version. The **inquiry-response layout** differs from Shimmer3R (a 4-byte config word instead of 7, so numChannels/channels sit at different offsets) and is ported from `ShimmerObject#interpretInqResponse` (HW_ID.SHIMMER_3 branch) — see `interpretShimmer3InquiryResponse`. v1 covers the connect handshake, inquiry/config read, `setSensors` / `setSamplingRate` / `setGSRRange` / `setInternalExpPower`, and start/stop streaming (a working schema-driven stream parser is included so streaming is not precluded, though full stream decoding is a later phase). New exports: `Shimmer3Client`, `Shimmer3ClientOptions`, `SHIMMER3_DEFAULTS`, `SHIMMER3_SPP_UUID`, `SHIMMER3_SAMPLING_CLOCK_FREQ`, `FW_ID`, `interpretShimmer3InquiryResponse`, `buildShimmer3Schema`, `parseShimmer3DeviceVersionResponse`, `parseShimmer3FwVersionResponse`, `shimmer3UsesThreeByteTimestamp`, `shimmer3ControlMessageLength`, and the inquiry-offset / response-length constants.
- **Pluggable transports (Phase 1 transport abstraction).** Device clients are now transport-agnostic: the raw Web Bluetooth / Web Serial byte plumbing is extracted behind a `ShimmerTransport` interface (`connect` / `disconnect` / `write` / `onNotify` / `onDisconnect`, plus a `capabilities` hint `{ maxWriteBytes?, framed }`). New exports: `WebBluetoothTransport` (parameterised by service / write / notify UUIDs), `WebSerialTransport`, and `LoopbackTransport` (in-memory, for tests), plus the `ShimmerTransport` / `TransportCapabilities` / `TransportScanner` types. `Shimmer3RClient` and `VerisenseBleDevice` accept an injected transport (constructor option or `connect(transport)` parameter) and otherwise build the appropriate web transport on `connect()` / `connectSerial()`, so existing browser usage is unchanged (no API break). Transports do **no** protocol interpretation and preserve notification chunk boundaries exactly, so Shimmer3R's ACK-with-piggybacked-response handling is unaffected. This lets non-browser runtimes (React Native / `react-native-ble-plx`, Bluetooth Classic) supply their own transport, and lets the client connect/inquiry/config flows be unit-tested against `LoopbackTransport` without a browser.
- `isVerisenseLipoBatteryHardware` (DEV-809) — hardware models with a permanently attached rechargeable LiPo battery (SR62 any revision, SR61.5+, SR68.9+), mirroring the firmware's `ShimBrd_isLipoPresentForHwVersion`. ### Fixed

- **Enabling the pressure sensor silently corrupted every channel after it in the packet.** A streaming data frame is a preamble byte, a timestamp, and then each enabled channel's bytes back to back in the order the inquiry listed them — there is no per-channel length, so the channel ID is the only thing that says how wide a channel is. Both schema builders (`Shimmer3RClient` and `buildShimmer3Schema`) assumed **2 bytes, little-endian, signed** for any ID they did not recognise, and they did not recognise `BMP_PRESSURE` (0x1B) or `BMP_TEMPERATURE` (0x1A). Pressure is 3 bytes on both platforms, and temperature is 3 bytes on a Shimmer3R, so a Shimmer3 packet was 1 byte longer than the SDK computed and a Shimmer3R packet 2 bytes longer. Nothing threw and nothing warned: the channels after pressure decoded from the wrong offset into plausible-looking numbers, and the frame size being wrong also stopped the byte-stream parser resynchronising at all. This was reachable from any host that simply switched the sensor on — pressure/temperature is stock hardware and one config bit (`chEnPressureAndTemperature`).

  The pair is now described per generation, from the firmware: a Shimmer3 reads BMP180/BMP280 over I²C and packs 2 big-endian bytes of temperature followed by 3 big-endian bytes of pressure (`LogAndStream_Shimmer3/i2c.c:389-394`, with `BMPX80_TEMP_BUFF_SIZE 0x02` / `BMPX80_PRESS_BUFF_SIZE 0x03` in `Shimmer_Driver/BMPX80/bmpX80.h:103-105`), while a Shimmer3R reads BMP390/BMP581 over SPI and packs 3 little-endian bytes each, **pressure first** (`LogAndStream_Shimmer3R/Core/Src/spi.c:739-756`). Note that the order of the pair is reversed between the two generations, which is one more reason a host must take the channel order from the inquiry response rather than from a list of its own. The other twelve previously-undescribed IDs — `VBATT`, the six external/internal ADC lines, the three alt-magnetometer axes, and the two bridge-amplifier channels — are all 2 bytes, so those were decoding at the right offsets all along and only the field **name** and signedness were wrong; they are now named and typed properly too. Values are raw only: BMP pressure compensation needs the sensor's coefficient blocks and is separate work. **HARDWARE-VERIFY: widths, byte orders and emission orders are taken from the firmware sources and pinned by unit tests, but no packet from a real sensor with pressure enabled has been decoded yet — on either generation.**

- **An unrecognised channel ID no longer fails quietly.** The fallback still assumes `UNKNOWN_CHANNEL_ASSUMED_BYTES` (2) and still names the field `CH_xx`, so one unfamiliar channel does not cost the whole packet and a consumer already reading `CH_xx` fields keeps seeing them — but the guess is now on the record: the ID appears in `schema.unknownChannelIds`, the field carries `assumed: true`, every field from that point on carries `offsetTrusted: false`, `schema.trusted` is `false`, and a status message names the ID and its position in the channel list. A host should treat those fields as unusable rather than record them, and update the SDK. Replaces a bare `console.warn` that fired for every channel without a sensor-enable bit — including well-known ones — and said nothing about widths. The same flags cover the case where `Shimmer3RClient` had to assume the hardware generation: if the channel list contains nothing whose decoding depends on it, the schema stays trusted; if it does, `trusted` is `false` and the message says to call `readDeviceVersion()` before `inquiry()`.

- **The ExG register banks were unreachable through the field schema.** `SHIMMER3_INFOMEM_FIELD_SCHEMA` described `exg1` and `exg2` correctly — the 10-byte ADS1292R chip-1 and chip-2 register banks at bytes 10-19 and 20-29 — but declared them `kind: 'u8'`. A generic editor built from the schema therefore offered a single 0-255 spinner for byte 10 (and byte 20) and left the other nine bytes of each bank with no way to read or write them, so an ExG configuration could not be edited by field at all. Both fields are now a new `bytes10` kind, handled by `readInfoMemFieldValue`/`writeInfoMemFieldValue` exactly as the existing `bytes21` calibration blocks are: a verbatim `Uint8Array` round-trip of the whole run, writing only the ten bytes it owns. `InfoMemDeviceConfig.exg1`/`exg2` are unchanged — they were already `Uint8Array`.

- **A Shimmer3R over a byte stream resynchronised straight past four responses it can now expect.** `shimmer3rControlMessageLength` could not frame the instream status (`[0x8A][0x71]…`) or battery (`[0x8A][0x94]…`) replies — 0x8A turns out to be a shared prefix rather than an opcode, and `sdMessageSpan` returned RESYNC for anything behind it that was not an SD frame — nor `WR_ACCEL_RANGE_RESPONSE` (0x0A) or `GYRO_RANGE_RESPONSE` (0x4A), which were absent from the fixed-length table. Each was stepped over one byte at a time and the command awaiting it timed out. `RSP_CALIB_DUMP` (0x99) is now framed too, as `[len][offset u16][data]` where the length byte counts the data only. STATUS_RESPONSE's length depends on which platform answered rather than on the bytes, so the framer takes a new optional `{ statusPayloadBytes?: 1 | 2 }` (default 2) that `Shimmer3RClient` supplies from `readDeviceVersion` — guessing high on a Shimmer3 does not stall, it swallows the byte after the status, usually the next command's ACK. New export: the `Shimmer3RFramingOptions` type. Affects Web Serial over USB and the virtual COM port a classic-Bluetooth pairing creates; the BLE path is unchanged. **HARDWARE-VERIFY: framing is unit-tested including boundaries and resync, but not yet run against a real serial or RFCOMM link.**

- **`Shimmer3RClient` waited out the ACK timeout on a NACKed command.** 0xFE was ignored, so a command the firmware refuses — several are refused outright while the device is sensing (`ShimBt_isCmdBlockedWhileSensing`), as is the data-rate test — failed 1.5 s later with "ACK timeout", which reads as a dead link rather than a refusal. It now rejects immediately with "NACK received", matching `Shimmer3Client`. There is no stray-byte risk to guard against here (unlike the classic client's `_awaitCmd` gate): the ACK handler only exists while a command is in flight, and every byte goes to the stream buffer while streaming, so a 0xFE sample byte never reaches the control fan-out. **HARDWARE-VERIFY: no repro against firmware; behaviour is unit-tested.**

- **Gen-2 GSR decoded with the wrong front-end constants when the hardware revision said otherwise** (DEV-874). `SensorADC` selected the second-generation DC front-end constants (21/150/562/1740 kΩ feedback resistors, 0.4986 V GSR reference, 1.8 V ADC reference, range-3 uncal limit 1134) only when the caller-supplied identifier string was `VERISENSE_PULSE_PLUS`; any other identifier fell back to the SR62/Shimmer3 set (40.2/287/1000/3300 kΩ, 0.5 V, 3.0 V, 683), reading ~1.91× high on an SR61-5/6. Selection now follows the production-config hardware revision (SR62 → Shimmer3 set, every other GSR-capable board → gen-2 set, mirroring the firmware's `selectFeedbackResistorsFromHwVersion`), with the identifier string kept only as the fallback before a revision is read. Verified against the DEV-793 33 k/100 k/470 k/2.7 MΩ resistor sweep on a real SR61-5. Also adds `isVerisenseGsrSupportedHardware` (mirrors the firmware's `ShimBrd_isGsrSupportedForHwVersion`: SR62 any / SR61 ≥ 5 / SR68 ≥ 5) and corrects `getVerisenseHardwareSensorSupport` to report GSR on SR68.5–8.
- **LSM6DSV gyro ~12.8% low without device calibration** (DEV-874). The no-calibration fallback in `SensorLSM6DSV` scaled the gyro by `FS/32768`, but the LSM6DSV gyro does not span the 16-bit range at nominal full scale — the ST angular-rate sensitivity is 4.375 mdps/LSB at ±125 dps, doubling per range (228.571/114.286/57.143/28.571/14.286 LSB per dps). A raw 32767 at ±500 dps now reads ~573.4 dps (was 500.0), matching the device calibration seed, `calibrationDefaults`, and the Java driver fix. Gyro CSVs exported before this fix (when no device calibration was loaded) are ~12.8% low. The accel fallback (`FS/32768 · g`) is unaffected and correct.
- `VerisenseBleDevice.stopStreaming()` is now best-effort and always reconciles state. Previously it awaited the STREAM_MODE-disable ACK and only then set the mode to idle / emitted `streaming:{on:false}`; at high data rates that ACK is easily lost (BLE notifications are unacknowledged and can be dropped under throughput pressure, and the in-flight stream tail is parsed by the command path rather than the CRC-gated stream scanner once streaming mode is left), so the awaited request timed out, the method threw, and the client stayed wedged in `streaming` — locking the UI even though the device had stopped. Stop now sends the disable as a **write-with-response** (link-layer delivery confirmation) and reconciles state (`idle`, assembler reset, `streaming:{on:false}`) in a `finally`, so a missing app-level ACK can no longer leave the client stuck. Mirrors the best-effort stop already used by `Shimmer3RClient`.
- Achieved sample rate (`StreamLossStats.windowSampleRateHz`) is now measured over the device-clock span of the windowed samples (first sample of the oldest packet to last sample of the newest) instead of the fixed host receive-time window. This is robust both to bursty BLE delivery and to large packets — a single packet carrying hundreds of samples spanning several seconds (e.g. a high FIFO watermark) no longer over-reports the rate. A stalled stream still reads 0.
- Live stats no longer flicker to 0 for streams that deliver less often than the stats window — e.g. a high FIFO watermark (one big read every few seconds) or a slow sensor at 1 Hz. The rate/throughput rings now always retain the last delivery, throughput/packet-rate are computed over the actual receive span (not a fixed 2 s), and a stream is only treated as stalled (→ 0) when its newest packet is older than a multiple of its own observed packet interval.

### Changed

- The Verisense LSM6DSV (id 6) data block now stores its entry count as a **2-byte little-endian** value (was 1 byte), so a full FIFO drain of more than 255 samples per read decodes correctly. Requires matching firmware (the firmware writes the 2-byte count and drains the full FIFO each interrupt).
- The MLX90632 skin-temperature config is now a **single "Skin Temp Sample Rate"** field (op-config byte 76 bits 3:1), shown as the medical output rate (0.25–32 Hz; = chip refresh ÷2, extended ÷3). The firmware applies the chip refresh rate from it and derives the read poll. The separate `SKIN_TEMP_SAMPLE_RATE_INDEX` (byte 77) and `SKIN_TEMP_POWER_MODE` (byte 76 bits 5:4) fields are removed from the schema and left unused in the op-config layout (continuous mode is required and set automatically). `SensorMLX90632.samplingRateHz` now derives from the refresh rate + measurement type. Requires matching firmware.
- The VD6283 **"Light Continuous Mode"** option is removed from the schema (op-config byte 74 bit 0 is now unused — free to repurpose): the timer-driven poll requires the chip to run continuously, so the firmware hardcodes it.
- The VD6283 **"Light Gain"** and **"Light Exposure"** op-config fields now render as labelled dropdowns (gain `1.0x`..`66.67x`; exposure `100 ms`..`204.8 ms`) instead of raw 0–7 indices. The default (index 0) is `1.0x` gain and `100 ms` exposure, matching the VD6283 reference example. Each exposure option is annotated with the max sample rate it allows (≈ 1/exposure).
- The VD6283 **inter-measurement time** is now coupled to the configured sample rate: the firmware sets the continuous-mode cadence to the sample period (clamped to ≥ the exposure) instead of a fixed 100 ms, so the sensor only measures as often as it is read (lower power at low rates). Because of this the **20 Hz** light rate is re-enabled (previously trimmed) — it is reachable when the exposure is ≤ 50 ms; the achievable rate is now bounded by `1/max(exposure, sample period)`. Requires matching firmware.
- The VD6283 **"Light Dark Channel"** option (op-config byte 74 bit 1) is now honored end-to-end. Firmware applies it via `LIGHT_SENSOR_CTRL_DARK` (previously the bit was a no-op). `SensorVD6283` now surfaces the dark reading as a **distinct `DARK` channel** rather than overloading `VISIBLE`: slot 1 is visible-or-dark and the two are mutually exclusive, so each `VD6283Sample` has exactly one of `VISIBLE` / `DARK` as a number and the other `null` (lux/CCT are unaffected — they derive from RED/GREEN/BLUE). For offline parsing, the firmware packs the dark-channel bit into **bit 7 of the existing light-gain header byte** (config-header byte 30; gain index stays in bits 2:0) so the separate file parser can label slot 1 correctly without lengthening the header or changing the firmware version. Requires matching firmware.

### Changed

- Verisense magnetometer config is now a single **Mag Output Rate** setting (the LSM6DSV sensor-hub rate). Operational-config byte 20 bits 1:0 are repurposed from the raw LIS2MDL ODR to an output-rate code (`0`=15, `1`=30, `2`=60, `3`=120 Hz); the firmware derives the underlying LIS2MDL ODR. `SensorLSM6DSV.magHz` now reports this output rate, and stream-loss for the mag is measured against it. Requires matching firmware (sensor-hub rate no longer hardcoded to 15 Hz).
- Live stream-loss is measured against each stream's **configured** sampling rate (not a derived "actual" rate), so a firmware/hardware/exposure shortfall surfaces as loss rather than being hidden. The VD6283/MLX90632 report their configured poll rate and the LSM6DSV mag reports its configured output rate (no longer capped at the accel/gyro hub-trigger rate). Op-config rate options are trimmed to physically-reachable values (e.g. the VD6283 light rate is bounded by the exposure time — see the dedicated entry above).

### Documentation

- **The README's device table said the wrong thing about two radios, and two different things about one link.** Both are Mark's findings:

  - Every Shimmer3 was listed as one row with one radio. Boards up to expansion-board revision 5 carry an **RN42**, classic Bluetooth only; revision 6 and later carry an **RN4678**, which is dual-mode, and the firmware picks the radio from two EEPROM bits at start-up (`ShimBt_startCommon`) — forcing classic Bluetooth on a unit with no EEPROM precisely because that is the RN42 fleet. So "Shimmer3 has no BLE" was true of the fleet the table was written against and false of the boards shipping now. BLE on an RN4678 works but is slow (LiteProtocol over the module's transparent-UART service), which is why classic Bluetooth stayed the streaming link; the SDK has no transport for it, and that is now said rather than implied by omission.
  - `Shimmer3 (classic BT)` described its link as "RFCOMM/SPP — Web Serial over a paired COM port" while `Shimmer3R` said only "Web Serial (USB or Bluetooth port)", as though the two devices reached classic Bluetooth by different routes. They do not: it is the same API, the same `WebSerialTransport`, the same `SHIMMER3_SPP_SERIAL_OPTIONS` and the same requirement that the host has already paired the sensor. What the Shimmer3R row was really collapsing is that "Web Serial" means two unrelated things on it — the LiteProtocol over a paired Bluetooth port, and the dock protocol over USB-C, with a different client for each. A new **Link Types** table separates link from API from transport so neither confusion can be read back out of it.

  Added with them: a **Browser Support** table (both APIs, the directory picker the SD download needs, and the iOS and Android rows that are not feature-detectable) and an **OS Support** table per link, carrying the three cells that need prose — Android's LE-bond trap, Android's RFCOMM-only Web Serial, and classic Bluetooth being impossible rather than absent on iOS. All three are the hardware-confirmed findings already documented in `platformSupport.ts`; the tables point at `describePlatformSupport` / `transportAvailability` / `transportAdvice` rather than inviting a page to re-derive them.
